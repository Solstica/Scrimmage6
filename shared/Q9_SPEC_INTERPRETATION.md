# 第9题官方说明的统一解释与建模边界

状态：`DRAFT / NEEDS_REVIEW`

本文件只解释题目“说明”对时间轴、输入/输出、约束与四问耦合关系的强制含义。它属于跨问共享规范，不替代各问正式模型、代码和 `results/registry.csv`。凡未由题面直接给出的处理均显式标为“建模解释/NEEDS_REVIEW”。

## 1. 六个时间集合必须分开

题目同时存在任务到达、预测评价、任务执行和能源状态四类时间语义，后续代码不得统一用一个模糊的 `0..2406` 时域。

| 集合 | 时段 | 含义 |
|---|---|---|
| `T_fit` | 0--2351 | Q1 预测参数估计 |
| `T_val` | 2352--2375 | Q1 模型选择/调参验证 |
| `T_test` | 2376--2399 | Q1 独立预测评价 |
| `T_main` | 0--2399 | Q2--Q4 主运行时域，也是唯一产生新任务的时域 |
| `T_drain` | 2400--2405 | 不产生新任务，仅结清已经到达但尚未完成的弹性任务；其能源、成本和碳排继续结算 |
| `T_terminal` | 2406 | 不安排未完成任务，只做电力与储能终端状态结算 |

由此定义：

- 任务允许占用的离散小时集合为 `T_exec = 0..2405`；
- 能源/储能状态至少需要覆盖 `T_energy = 0..2406`；
- Q1 最后 24 h 预测评价和最后 24 h 正式调度是两条不同流程。

### 1.1 任务截止边界

若任务 `i` 开工时刻为 `s_i`，持续时间为 `p_i = EstimatedDuration_min/60` h，则必须满足

`finish_i = s_i + p_i <= 2406`。

任务占用采用半开区间 `[s_i, finish_i)`，因此“在时点 2406 完成”合法，但任务不能占用第 2406 小时 `[2406,2407)`。

### 1.2 2400--2405 的正确含义

题面只禁止这 6 个小时产生新任务，并未禁止已经等待的 BatchInference / AITraining 在此期间开工。因此可在 2400--2405 安排此前到达的弹性任务，只要其完成时刻不超过 2406。

### 1.3 小时级开工时刻的建模解释

`NEEDS_REVIEW`：根据 1 h 数据粒度、ArrivalHour/EarliestStartHour/LatestFinishHour 的字段形式以及逐小时容量/电力参数，当前统一解释为 `s_i` 取整数小时边界；Duration 仍保留分钟精度，通过与每个小时的实际重叠长度计入 GPU-hour 和 AI IT 能量。若附件原文另有连续开工时刻定义，应以原文为准。

## 2. Q1 的“训练/验证/测试”不等于机器学习

官方说明给出的 0--2351 / 2352--2375 / 2376--2399 划分只规定预测模型的参数估计、模型选择和最终独立评价流程，并未要求神经网络或其他黑箱模型。

统一论文表述建议：

- 0--2351：参数估计区间；
- 2352--2375：模型选择区间；
- 确定模型后，用 0--2375 重估参数；
- 2376--2399：独立测试区间。

Q1 正式基础调度使用 2376--2399 的实际到达任务，因此预测误差不向 Q1 调度、Q2、Q3、Q4 传播。

## 3. 输入参数、基准结果和优化结果必须严格区分

官方说明要求 Q2--Q4 按实际到达任务、实际逐时电力参数和统一功率映射重新计算。由此形成唯一允许的数据因果链：

`actual workload -> (region,start) decision -> overlap/GPU-hour -> AI IT load -> total IT load -> facility load -> renewable/grid/storage allocation -> cost/carbon/renewable utilization/peak`。

### 3.1 调度问的 AI IT 功率

Q1、Q2、Q4 的任务形成 AI IT 功率时，只能使用 `power_mapping.xlsx` 的统一映射。不可直接继承 baseline 的 AI IT 结果，也不可另拟 GPU 功率参数。

若 `omega_i,t(s_i)` 为任务 i 与小时 t 的实际重叠时长（h），任务类型单位 GPU 功率为 `alpha_type`，则 AI IT 能量贡献为

`alpha_type * GPU_i * omega_i,t` (MWh)，

在 1 h 时隙下对应的小时平均 AI IT 功率数值为同一数值（MW），但论文必须区分功率与能量单位。

### 3.2 统一硬约束

凡涉及任务调度的 Q1、Q2、Q4，必须同时满足：

- GPU 容量；
- IT 功率上限；
- 设施功率上限；
- 网络时延 SLA；
- EarliestStart / LatestFinish / 2406 完成边界；
- NonPreemptive、不可拆分、执行中不可迁移。

网络时延首先作为可执行区域的硬可行性条件，不得用“较低时延得分”替代 SLA 检查。

## 4. Q3 是固定算力负荷下的受控能源实验

Q3 不读取任务层决策变量重新安排工作负载。它固定：

- `Baseline_AI_IT_Load_MW`；
- `NonAI_IT_Load_MW`；
- 区域 PUE。

并由“给定 IT 负荷 × PUE”得到设施负荷，只释放：

- 储能充/放电；
- 电网购电；
- 新能源使用；
- 允许区域的售电。

因此 Q3 在全文中的作用是隔离“储能/电力柔性”的独立贡献。Q2 隔离“算力时空柔性”，Q4 再联合二者。这一解释应保持 DS-REPTA 四模式统一，而不是把 Q3 写成另起炉灶的模型。

## 5. SOC 时间索引必须按官方口径重写

`InitialSOC_MWh` 是第 0 小时运行前的唯一初始状态；`region_time_data.xlsx` 的 `SOC_MWh(t)` 是第 t 小时运行后的时段末基准状态。

统一索引：

- `S_r,-1 = InitialSOC_r`；
- 对 `t = 0..2406`，`S_r,t` 表示第 t 小时运行后的 SOC；
- 递推形式写为 `S_r,t = S_r,t-1 + eta_c * P_ch,r,t * Delta_t - P_dis,r,t/eta_d * Delta_t`；
- 终端约束为 `S_r,2406 >= InitialSOC_r`。

这比使用含糊的 `SOC(t+1)=...` 更不容易出现一小时错位。

### 5.1 2406 的终端能源结算

题面明确 2406 不安排未完成任务，但允许作为“电力与储能终端状态结算”时段。`NEEDS_REVIEW`：当前实现原则为，若 2406 发生购电/售电/充放电以满足终端 SOC 或电力平衡，则对应能源流不能成为免费操作，应进入统一电力平衡及相应结算。需结合附件 1 对成本/碳统计区间的原始公式最终确认。

## 6. 2400--2406 防止两类“时域外借资源”

任务侧要求全部任务在 2406 前完成，可写成计算队列终端清零；储能侧要求 `SOC(2406) >= InitialSOC`。两者共同防止优化器制造虚假收益：

- 把计算任务推到研究时域之外；
- 在最后阶段把电池放空，把恢复成本推到研究时域之外。

可在 Q4 统一称为“算力队列—储能状态双终端约束”，但该命名属于论文表达，不是题面术语。

## 7. Q4 明确禁止自行补充的模型

官方说明明确不要求建立：

- 线路潮流；
- 网络带宽；
- 迁移数据量；
- 传输能耗；
- 传输费用。

因此跨区任务分配的网络侧只使用题目给定的 `network_latency.xlsx` 与任务 `MaxLatency_ms` 构造可行区域集合。除非题目目标函数另有明确要求，不自行增加迁移费用、传输能耗或带宽拥塞惩罚。

这也意味着 DS-REPTA 的候选评分应由题目真实提供的能源经济、碳、等待/完成压力及资源容量信息组成；网络延迟先做硬剪枝，而不是虚构通信代价。

## 9. 对 DS-REPTA 的直接算法后果

1. **先合法化再优化**：构造 `(region,start)` 候选前先应用 Arrival/EarliestStart、LatestFinish、2406、MaxLatency 和任务类型规则。
2. **任务时域和能源时域分离**：任务只占用 0--2405，能源/储能结算延伸到 2406。
3. **预测模块隔离**：Q1 预测只做独立评价，不进入 Q2--Q4 的实际任务流。
4. **统一 evaluator**：Q1/Q2/Q4 必须调用同一套 overlap、GPU-hour、power_mapping、PUE 和 carbon/renewable 计算内核，防止四问口径漂移。
5. **Q3 冻结 task layer**：同一 DS-REPTA 框架切换到 Energy-response mode，固定 baseline AI IT，不调用任务重排。
6. **网络只做 SLA gate**：禁止将不存在的带宽、迁移数据量、传输能耗/费用补进目标函数。
7. **终端边界进入可行性检查器**：任何候选任务若 `finish > 2406` 立即删除；2406 禁止任务占用。

## 10. 需要最终人工确认的两点

- `NEEDS_REVIEW`：开工时刻是否严格限定整数小时边界；当前依据 1 h 粒度采用整数时隙解释。
- `NEEDS_REVIEW`：2406 若发生纯终端充放电/购售电，其成本与碳排是否纳入最终统计；为避免“免费终端补能”漏洞，当前建议统一结算，但需以附件 1 原始公式最终确认。
