# Q2 绘图报告

本报告对应最新 `feature/q2` 的 iterative SFETA canonical 结果。Cost-primary 为 `reference-start` 三遍收敛端点，Carbon-primary 为同一 reference-start 的三遍收敛端点，另保留 `previous-start` 作为初始化稳健性对照。所有 CSV 均为“一图一表”，已使用 UTF-8 with BOM 编码，列名带有 Origin 绘图角色和单位，可直接导入 Origin 中文版。

## 二、Origin 作图步骤

### 图01 三类任务空间合法区域范围

- 数据表：`图01_任务空间柔性范围.csv`
- 选列：`X_任务类型`、`Y_空间合法区域数_下限_个`、`Y_空间合法区域数_上限_个`
- 图型：Origin 中文版选择“绘图”→“柱形/条形/饼图”→“浮动柱形图”（若版本没有浮动柱形，选择“区间柱形图”）。
- 设置：X 轴标题“任务类型”；Y 轴标题“空间合法区域数（个）”，范围 0–6.5；下限系列用浅蓝，上限系列用深蓝；显示上下限数据标签，保留 0 位小数；图例写“下限”“上限”。
- 结论：训练任务始终有 6 个合法区域，批量推理为 5–6 个，实时推理仅 1–3 个，空间迁移柔性由训练到实时明显递减。

### 图02 三类任务时间余量中位数

- 数据表：`图02_任务时间余量中位数.csv`
- 选列：`X_任务类型`、`Y_时间余量中位数_h`
- 图型：选择“绘图”→“条形图”→“水平条形图”。
- 设置：X 轴标题“时间余量中位数（h）”，Y 轴标题“任务类型”；条形统一使用青绿色；开启数据标签，保留 2 位小数；按“实时推理、批量推理、AI训练”顺序显示。
- 结论：实时推理的时间余量约 0.50 h，而批量推理和 AI 训练均约 1200 h，说明 RT 必须即时开工，弹性任务承担主要时间迁移空间。

### 图03 三类任务 GPU 小时中位数

- 数据表：`图03_任务GPU小时中位数.csv`
- 选列：`X_任务类型`、`Y_GPU小时中位数_GPU小时`
- 图型：选择“绘图”→“统计图”→“棒棒糖图”（或“绘图”→“基本二维图”→“散点图”，再将符号与基线设置为棒棒糖效果）。
- 设置：Y 轴标题“GPU小时中位数（GPU·h）”；X 轴标题“任务类型”；AI训练使用橙色，批量推理使用蓝色，实时推理使用灰色；显示 2 位数据标签；Y 轴从 0 开始。
- 结论：AI 训练单任务 GPU 小时中位数约 194.35，明显高于批量推理和实时推理，是优先保护资源容量的主要任务类型。

### 图04 Cost-primary 收敛与初始化路径

- 数据表：`图04_成本收敛轨迹.csv`
- 选列：`X_扫描轮次`、`Y_参考起点成本_CNY`、`Y_前次起点成本_CNY`
- 图型：选择“绘图”→“基本二维图”→“折线图”。
- 设置：X 轴标题“完整扫描轮次”；Y 轴标题“运行成本（CNY）”；参考起点用深蓝实线圆点，前次起点用橙色虚线方点；图例使用“reference-start”“previous-start”；Y 轴建议使用科学计数法或显示千分位；在第 3、4 个点添加数据标签。
- 结论：reference-start 在第 3 遍达到 1.555×10^9 CNY 并通过相对改善率门禁；previous-start 第 4 遍仍收敛到更高成本，表明启发式存在初始化路径依赖。

### 图05 两个目标端点的碳排收敛

- 数据表：`图05_碳排收敛轨迹.csv`
- 选列：`X_扫描轮次`、`Y_Cost主端点碳排_tCO2`、`Y_Carbon主端点碳排_tCO2`
- 图型：选择“绘图”→“基本二维图”→“折线图”。
- 设置：X 轴标题“完整扫描轮次”；Y 轴标题“碳排放（tCO2）”；Cost 主端点用深蓝，Carbon 主端点用绿色；打开圆点符号和图例；数据标签只保留第 3 遍端点值，保留 2 位小数。
- 结论：Carbon-primary 在各轮次碳排均低于 Cost-primary，但两条曲线走势高度一致，支持“Cost-primary 主规则 + Carbon-primary 对照端点”。

### 图06 三种端点运行成本

- 数据表：`图06_方案运行成本对比.csv`
- 选列：`X_方案`、`Y_运行成本_CNY`
- 图型：选择“绘图”→“柱形/条形/饼图”→“柱形图”。
- 设置：Y 轴标题“运行成本（CNY）”；Cost 主端点用深蓝，Carbon 主端点用绿色，前次起点 Cost 用橙色；显示千分位数据标签；Y 轴从 1.54×10^9 起时必须在轴标题或图注注明“截断坐标”，若强调绝对量则从 0 起。
- 结论：Cost-primary 为最低成本端点；Carbon-primary 只增加约 0.1789% 成本，目标冲突很小。

### 图07 三种端点碳排放

- 数据表：`图07_方案碳排放对比.csv`
- 选列：`X_方案`、`Y_碳排放_tCO2`
- 图型：选择“绘图”→“柱形/条形/饼图”→“柱形图”。
- 设置：Y 轴标题“碳排放（tCO2）”；Carbon 主端点用绿色，Cost 主端点用深蓝，前次起点用橙色；显示 2 位数据标签；与图06 使用相同类别顺序和画布宽度。
- 结论：Carbon-primary 碳排最低；Cost-primary 相比 Carbon-primary 仅多排约 11,242.75 tCO2（约 0.6193%）。

### 图08 任务类型等待分布

- 数据表：`图08_任务类型等待分布.csv`
- 选列：`X_任务类型`、`Y_平均等待_h`、`Y_等待P95_h`、`Y_最大等待_h`
- 图型：选择“绘图”→“柱形/条形/饼图”→“分组柱状图”。
- 设置：Y 轴标题“等待时间（h）”；平均等待用蓝色，P95 用橙色，最大等待用红色；图例显示三个统计量；显示标签时只给平均值和 P95，最大值可保留悬停/图注，避免 2016 h 造成标签拥挤。
- 结论：批量推理平均等待和最大等待最高，实时推理严格为零等待；长等待是能源目标利用长时间柔性的服务代价，不是 deadline 违规。

### 图09 区域迁移矩阵

- 数据表：`图09_区域迁移矩阵.csv`
- 选列：全部列，即 `X_来源区域` 和 6 列 `Y_区域*_任务数`。
- 图型：选择“绘图”→“等高线/热图”→“热图”（需要时在“矩阵转换”中将工作表转换为矩阵）。
- 设置：横轴为执行区域，纵轴为来源区域；色标标题“迁移任务数（个）”；使用浅黄—深红连续色带；打开单元格数值标签，保留整数；颜色范围固定为 0 到表中最大值，便于与其他版本比较。
- 结论：迁移不是均匀分布，部分来源区域明显向区域 C/E 集中，说明能源与容量状态共同形成了承接区域。

### 图10 Cost-primary 逐时能源状态

- 数据表：`图10_逐时能源状态.csv`
- 选列：`X_小时`、`Y_设施负荷_MW`、`Y_电网购电_MW`、`Y_弃电_MW`、`Y_利用新能源_MW`
- 图型：选择“绘图”→“基本二维图”→“折线图”。
- 设置：X 轴标题“小时（h）”，范围 0–2405；Y 轴标题“功率（MW）”；设施负荷用黑色粗线，电网购电用蓝色，弃电用橙色，利用新能源用绿色；只保留一组图例；线宽 1.2–1.5 pt；不要给 2406 添加任务曲线。
- 结论：调度负荷改变了逐时电网购电与弃电状态；利用新能源的增加与弃电降低应在同一时间轴上解释。

### 图11 任务负荷增量与能源响应

- 数据表：`图11_负荷增量与能源响应.csv`
- 选列：`X_任务负荷增量_MW`、`Y_弃电变化_MW`、`Y_购电变化_MW`
- 图型：选择“绘图”→“基本二维图”→“散点图”；将两列 Y 作为两个数据系列。
- 设置：X 轴标题“任务负荷增量（MW）”；Y 轴标题“能源响应变化（MW）”；弃电变化用橙色圆点，购电变化用蓝色方点；保留 0 参考线；不连接散点，不添加拟合线。
- 结论：负荷增量为负时，弃电和购电变化整体同步下降，说明调度结果通过基准状态增量能源响应同时改变弃电消纳和电网购电。

### 图12 成本—碳排端点关系

- 数据表：`图12_成本碳排端点散点.csv`
- 选列：`X_运行成本_CNY`、`Y_碳排放_tCO2`，`标签_方案`作为数据标签。
- 图型：选择“绘图”→“基本二维图”→“散点图”。
- 设置：X 轴标题“运行成本（CNY）”；Y 轴标题“碳排放（tCO2）”；Cost 主端点用深蓝圆点，Carbon 主端点用绿色菱形，前次起点用橙色方点；启用标签列 `标签_方案`；不连接散点，不添加拟合线。
- 结论：Cost-primary 与 Carbon-primary 位于相近的低成本、低碳区域，Carbon-primary 以很小成本增加换取更低碳排；previous-start 同时偏向更高成本和更高碳排。

## 三、极端等待审计

审计表：`../results/q2_extreme_wait_audit.csv`。该表不用于作图，而用于核对图08和论文解释。表中前 5 个任务全部满足 `完成时刻 <= 最晚完成时刻` 和网络时延上限；最大等待任务为 TaskID 13051，等待 2016 h、可用时间余量约 2331.93 h、网络时延 22 ms，小于 80 ms 上限。因此长等待来自能源导向调度对合法 slack 的使用，不是时间索引或 deadline bug。
